# Business Rules — CineBook

## 1. Document Purpose

This file is the **authoritative reference for CineBook business rules**.
It defines what the application must do, what is allowed, what is forbidden, and how conflicts should be resolved.

**Priority Rule**:
1. Rules in this document override generic framework patterns or AI preferences.
2. If this document contradicts `AGENTS.md`, `AGENTS.md` wins.
3. If this document contradicts existing working code, inspect whether the code was intentional before changing it.

---

## 2. Global Invariants

- All monetary amounts are stored in **VND** using `decimal(12, 2)` (or `decimal(10, 2)` for prices) and mapped to `BigDecimal` with rounding `HALF_UP`.
- All timestamps use **UTC+7** (Indochina Time / Asia/Ho_Chi_Minh).
- Entity primary keys are **UUID (CHAR(36))**, generated by the application/JPA (`seat_holds.id` is `bigint AUTO_INCREMENT`).
- Database constraints (foreign keys, `uk_*` unique keys, check constraints) are strictly enforced and must never be removed or bypassed.
- Sensitive credentials (passwords, tokens, payment secrets) must never be stored in plain text, logged, or returned in API responses.

---

## 3. Authentication & User

- User email is unique (`uk_users_email`), case-insensitive at check time.
- Passwords must be hashed using BCrypt before persistence.
- JWT expiration: **15 minutes** for Access Token, **7 days** for Refresh Token.
- Revoked or rotated refresh tokens cannot be used to issue new access tokens.
- User roles are `CUSTOMER` and `ADMIN`.
- A customer cannot access admin endpoints (`/api/v1/admin/**`) $\rightarrow$ `403 Forbidden`.
- An unauthenticated user cannot access protected endpoints $\rightarrow$ `401 Unauthorized`.
- Active user status: `ACTIVE`, `BLOCKED`. Blocked users cannot authenticate or initiate bookings.

---

## 4. Movie

- A movie may belong to multiple genres (`movies_genres`).
- `tmdb_id` is unique when present (one CineBook movie per TMDB movie).
- Soft-deleted movies (`deletedAt != null`) are hidden from public listings.
- Movie status values: `NOW_SHOWING`, `COMING_SOON`, `END_OF_SHOWING`, `HIDDEN`. Only `NOW_SHOWING` and `COMING_SOON` are visible in public listings.
- TMDB import/re-import: Re-importing updates external metadata (title, overview, duration, director, actors, release date, poster, backdrop, trailer, genres) while preserving CineBook lifecycle fields (`id`, `status`, `deletedAt`, `createdAt`).

---

## 5. Cinema, Auditorium, Seat

### 5.1 Cinema & Auditorium
- An auditorium belongs to exactly one cinema.
- Auditorium name is unique within a cinema (`uk_auditoriums_cinema_name`).
- Soft-deleted cinemas/auditoriums are excluded from public and booking flows.
- `rows_count` and `columns_count` must be > 0.
- Auditorium status: `ACTIVE`, `MAINTENANCE`. Only `ACTIVE` auditoriums can host scheduled showtimes.

### 5.2 Seat & Seat Type
- A seat belongs to exactly one auditorium and one seat type.
- Seat position (`row_label` + `seat_number`) is unique within an auditorium (`uk_seats_auditorium_row_number`).
- Seat type has a `price_modifier` $\ge 0$. Standard types: `STANDARD` (0 VND), `VIP` (+20,000 VND), `COUPLE` (+40,000 VND).
- Seat status: `ACTIVE`, `BROKEN`. Only `ACTIVE` seats can be held, reserved, or sold.

---

## 6. Showtime

- A showtime belongs to exactly one movie and one auditorium.
- `endTime` must be strictly greater than `startTime`.
- `basePrice` must be $\ge 0$.
- Showtime status values: `SCHEDULED`, `CANCELLED`, `FINISHED`.
- **Conflict Rule**: Overlapping showtimes in the same auditorium are forbidden (`startTime < existing.endTime && endTime > existing.startTime` for active non-cancelled showtimes).
- A showtime accepts new holds and bookings only when its status is `SCHEDULED` and `startTime > now` (representing active, open-for-booking schedule).
- Showtimes with status `CANCELLED` or `FINISHED`, or showtimes whose `startTime <= now`, strictly reject any new seat hold or booking creation.

---

## 7. Pricing

Pricing for a ticket is composed of:
1. Showtime `basePrice`
2. Seat-type `priceModifier` (from `seat_types`)
3. Showtime format / day / time rules when configured.

**Formula**:
$$\text{Ticket Gross Price} = \text{basePrice} + \text{priceModifier}$$
$$\text{Booking Gross Total} = \sum \text{Ticket Gross Prices}$$

## 8. Booking & Seat Hold (Critical)

### 8.1 Core Invariants
1. **A seat must not be sold or held more than once for the same showtime.**
2. A booking always belongs to one user and one showtime.
3. Booking total is calculated deterministically at reservation time and stored with an immutable snapshot.
4. Expired seat holds must not remain valid.
5. Payment status and booking status must stay strictly consistent.

#### 8.2 Seat Availability & Hold Rules
- A hold is recorded in `seat_holds` with a unique constraint on `(showtime_id, seat_id)` (`uk_seat_holds_showtime_seat`).
- Hold creation checks current availability (existing active holds + sold tickets in `VALID`/`USED` status).
- Seat-hold duration is strictly **5 minutes** (`holdExpiresAt = now.plusMinutes(5)`).
- Cleanup strategy: Active cleanup via `BookingCleanupTask` (scheduled every 60 seconds) plus lazy evaluation at check/creation time.
- **Seat Map Availability & Ownership**: Availability status enum remains strictly `AVAILABLE`, `HELD`, `SOLD`, `BLOCKED`. Authenticated user ownership is indicated via `isHeldByCurrentUser: boolean`. When a customer returns to a showtime with active holds, their seats are marked `isHeldByCurrentUser = true`, allowing seamless booking resumption.
- **Active Booking Resume**: An active `PENDING_PAYMENT` booking can be retrieved via `GET /api/v1/bookings/active?showtimeId={showtimeId}` or resumed idempotently upon re-submitting `POST /api/v1/bookings` with the identical showtime and seat set.

### 8.3 Booking Lifecycle
```text
PENDING_PAYMENT  ──(Payment SUCCESS)──►  PAID  ──(Refund SUCCESS)──►  REFUNDED
       │
       ├──(Hold Expired)──────────────►  EXPIRED
       └──(User/Admin Cancel)────────►  CANCELLED
```
- A booking moves to `PAID` only when payment is verified as successful via authoritative IPN callback.
- Tickets (`ticket_status = VALID`) are generated only upon transition to `PAID`.

## 9. Payment & Refund (Finalized V2)

### 9.1 Core Rules
- Payment verification **must** happen on the backend via VNPay Sandbox cryptographic signature (HMAC-SHA512).
- The VNPay IPN webhook (`/api/v1/payments/ipn`) is the authoritative source of truth. The frontend return URL is strictly read-only for UX.
- Booking becomes `PAID` only after a valid, verified IPN confirmation with response code `00`.
- Payment amount must match the booking total (`amount == booking.totalAmount * 100` in VNPay minor units).

### 9.2 Cardinality, State Consistency & Payment Resume/Retry
- **Cardinality**: `Booking 1 ─── N Payment`. A booking can have multiple payment attempts after `FAILED` or `CANCELLED` attempts.
- **Single Active Pending Payment**: At most one payment record in `PENDING` status per booking at any time.
- **Payment Resume (Idempotent Initiation)**: If a booking is in `PENDING_PAYMENT` and `holdExpiresAt > now`, calling `POST /api/v1/bookings/{id}/payments` when an active `PENDING` payment exists will **resume** the existing payment record (reusing the existing `Payment` row and returning a fresh, valid gateway URL) instead of rejecting with a 409 Conflict.
- **Payment Retry**: If a previous payment attempt was `FAILED` or `CANCELLED` (e.g. user cancelled on VNPay), and the seat hold is still valid (`holdExpiresAt > now`), the customer can initiate a new payment attempt (`POST /api/v1/bookings/{id}/payments`), creating a new `Payment(PENDING)` record.
- **Payment Statuses**: `PENDING`, `SUCCESS`, `FAILED`, `CANCELLED`, `REFUNDED`.
- **Financial Race Condition**: If payment succeeds but IPN arrives after booking expired, `Payment` becomes `SUCCESS`, `Booking` remains `EXPIRED`, zero tickets are issued, and a critical financial exception is audit-logged for Admin refund via `POST /api/v1/admin/bookings/{bookingId}/refund`.

### 9.3 Refund Invariants
- **Customer Refund** (`POST /api/v1/payments/{paymentId}/refund`): Allowed only for `SUCCESS` payment, `PAID` booking, and strictly $\ge 2$ hours before showtime `startTime`.
- **Admin Refund** (`POST /api/v1/admin/bookings/{bookingId}/refund`): Admin can refund any paid booking or orphaned successful payment without the 2-hour restriction.
- **Refund Transitions**:
  - `RefundStatus = SUCCESS`
  - `PaymentStatus = REFUNDED`
  - `BookingStatus = REFUNDED`
  - `TicketStatus = CANCELLED` (all tickets belonging to the booking)
  - Seats are immediately released and become available for new reservations.
  - Promotion quota (`usedCount`) is NOT incremented/re-consumed; discount remains immutable snapshot.

## 10. Promotion & Voucher Management (Finalized V1)

- **Uniqueness**: Promotion code is unique (`uk_promotions_code`), uppercase alphanumeric.
- **Validity Window**: Valid if and only if `startAt <= now < endAt` and `status == ACTIVE`.
- **Discount Types**:
  - `PERCENTAGE`: $\text{discount} = \min(\text{grossAmount} \times \text{discountValue} / 100, \text{maxDiscountAmount})$.
  - `FIXED_AMOUNT`: $\text{discount} = \min(\text{discountValue}, \text{grossAmount})$.
- **Order Minimum**: If `minOrderAmount` is present, `grossAmount` must be $\ge \text{minOrderAmount}$.
- **Net Total Invariant**: $\text{booking.totalAmount} = \max(0, \text{grossAmount} - \text{discountAmount}) \ge 0$.
- **Stacking Policy**: Strictly **at most 1 promotion per booking** in V1 (no stacking).
- **Usage Limit & Concurrency**: `usedCount <= usageLimit` (when limit is configured), protected via pessimistic locking (`SELECT ... FOR UPDATE`).
- **Quota Release**: Expired or cancelled `PENDING_PAYMENT` bookings release their `usedCount` reservation (`usedCount = max(0, usedCount - 1)`).
- **Immutable Snapshot**: When applied, `discountAmount` is snapshotted into `booking_promotions`.

## 11. Reporting & Dashboard (Finalized V1)

- **Gross Revenue**: Sum of payments in `SUCCESS` and `REFUNDED` status based on `payment.paidAt`.
- **Refund Amount**: Sum of refunds in `SUCCESS` status based on `refund.processedAt`.
- **Net Revenue**: $\text{Gross Revenue} - \text{Refund Amount}$.
- **Gross Tickets Sold**: Count of tickets in bookings with status `PAID` or `REFUNDED`.
- **Refunded Tickets**: Count of tickets with status `CANCELLED` in `REFUNDED` bookings.
- **Net Tickets Sold**: $\text{Gross Tickets Sold} - \text{Refunded Tickets}$.
- **Showtime Capacity**: Count of `ACTIVE` seats in the showtime's auditorium.
- **Occupied Seats**: Count of tickets with status `VALID` or `USED` for that showtime.
- **Occupancy Rate**: $\frac{\text{Occupied Seats}}{\text{Total Capacity}} \times 100\%$ (guarded against division by zero: returns `0.00%` when capacity is 0).

## 12. Soft Delete Behavior

Entities supporting soft delete (`users`, `movies`, `cinemas`, `auditoriums`):
- Soft delete sets `deletedAt = LocalDateTime.now()`.
- Soft-deleted records are automatically filtered out from public customer APIs and active booking flows.
- Hard delete is forbidden on transactional entities (`payments`, `refunds`, `bookings`, `tickets`).

## 13. Summary of Hard Invariants (Must Never Be Violated)

| # | Invariant |
|---|-----------|
| 1 | A seat cannot be sold more than once for the same showtime |
| 2 | Booking always references a valid user and showtime |

| 4 | Payment success is verified on the backend before booking becomes PAID |
| 5 | Payment status and booking status remain consistent |

| 7 | Authorization respects the authenticated user’s roles |
| 8 | Secrets (passwords, tokens, gateway keys) are never exposed or logged |
| 9 | Monetary amounts are never negative |
